Round-robin writes across two independent Supabase projects, wired together with PostgreSQL bidirectional logical replication. Both nodes stay fully writable — no primary, no replica, no promotion on failover.

How it works ↓ Read the code
PostgreSQL WAL-level replication

Changes flow at the database level.

Each node publishes its local writes via a logical publication. The other node subscribes with origin = none — so only rows written directly on the publisher are forwarded. Replicated rows are never re-published. No loops. No application glue required.

Why origin = none breaks the loop.

PostgreSQL's WAL tracks the origin of every record. When Node B applies a row replicated from Node A, that row is stamped with the subscription origin. Node B's publication only broadcasts rows with no origin — rows written directly by an application. The replicated row is invisible to the publisher, so it is never sent back to Node A.

Both nodes, always writable

No primary. No replica. No promotion.

Traditional primary/replica setups leave one node read-only until a failover promotion completes. BDR removes that constraint entirely.

Live failover · zero promotion

HAProxy in front. Instant switchover.

Because both nodes are always writable and always current, HAProxy's health check is the only thing standing between an outage and continued service. When Node A fails its checks, traffic moves to Node B — which is already accepting writes.

Active / Passive failover

All traffic hits Node A. Node B takes over only on failure.
  • ✓Deterministic routing — easier to reason about
  • ✓No cross-node conflict risk
  • ›Node B is idle until needed — wasted capacity

Active / Active load balanced

Traffic round-robins across both nodes. Either failure halves capacity.
  • ✓Both nodes serve traffic — full utilization
  • ✓Matches what the app's write API already does
  • ›Simultaneous writes to the same row → last-write-wins
# Active/passive — balance first + backup flag backend supabase_nodes balance first option httpchk GET /rest/v1/items?limit=1 http-check expect status 200 server node-a <ref-a>.supabase.co:443 ssl verify none check inter 2s fall 3 rise 2 weight 100 server node-b <ref-b>.supabase.co:443 ssl verify none check inter 2s fall 3 rise 2 backup # Active/active — swap balance and drop backup backend supabase_nodes balance roundrobin ... server node-a <ref-a>.supabase.co:443 ssl verify none check inter 2s fall 3 rise 2 server node-b <ref-b>.supabase.co:443 ssl verify none check inter 2s fall 3 rise 2

BDR means writes that land on Node B during an outage are not lost.

When Node A recovers, its subscription to Node B resumes from the replication slot's last confirmed LSN. Any writes Node B accepted during the outage replicate back automatically — no manual sync, no reconciliation.

Up in five minutes

Run it yourself.

Two Supabase projects, four SQL files, one Next.js app. The SQL sets up the schema, a dedicated replication user, publications, and subscriptions. The app runs against your credentials from .env.local.

# 1. Clone and install
git clone https://github.com/brendan-stephens/supabase-bdr
cd supabase-bdr
npm install

# 2. Create two Supabase projects, then run sql/ in order on each
#    01_schema.sql          — both nodes
#    02_replication_user.sql — both nodes
#    03_publications.sql     — both nodes
#    04_subscriptions.sql    — node-specific (see comments in file)

# 3. Configure credentials
cp .env.example .env.local
#    fill in NODE_A_URL, NODE_A_ANON_KEY, NODE_B_URL, NODE_B_ANON_KEY

# 4. Run
npm run dev                 # http://localhost:3000
# Script two concurrent inserters against the HTTP API
inserter() {
  local name=$1; local n=0
  while true; do
    curl -s -X POST http://localhost:3000/api/write \
      -H "Content-Type: application/json" \
      -d "{\"content\": \"$name #$((++n))\"}" \
    | jq -r '"[\(.writtenTo)] \(.item.content)"'
    sleep 0.5
  done
}
inserter "alice" &
inserter "bob" &
wait   # Ctrl-C to stop
1

2

3

Replication lag is a function of network RTT. Same-region projects replicate in tens of milliseconds. Cross-region adds RTT but both nodes remain writable throughout.

4

Conflicts default to last-write-wins. For most workloads with round-robin routing, conflicts are rare. For high-contention rows, add application-level versioning or use a dedicated BDR solution.
